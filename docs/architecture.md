# 架构说明

## 数据流

```
┌──────────────────┐
│  备用机（安卓）    │
│  SmsForwarder    │
└────────┬─────────┘
         │ HTTPS POST /hook/<hookToken>
         │ from=&content=&timestamp=&sign=
         ▼
┌──────────────────────────────────────────────┐
│  server.js                                    │
│                                               │
│  ① 校验 hook 令牌（可选再校验 HMAC 签名）        │
│  ② 去重（dedupeSeconds 内同号码同内容只收一次）  │
│  ③ 过滤（关键词 / 黑白名单）                     │
│  ④ 提取验证码，写入存储                          │
│  ⑤ 立刻回 200（手机端不阻塞）                    │
│  ⑥ 异步投递邮件，失败按退避重试                   │
└───────┬───────────────────────┬──────────────┘
        │                       │
        │ 写入                   │ SMTP（465 / 587）
        ▼                       ▼
   data/messages.json      收件邮箱
        │
        │ SSE 推送
        ▼
   网页收件箱（public/）
```

## 模块职责

| 文件 | 职责 |
| --- | --- |
| `server.js` | HTTP 路由、鉴权、限流、Webhook 入库、重试队列、SSE 广播 |
| `lib/config.js` | 配置加载/保存、令牌生成、前端配置脱敏、配置补丁清洗 |
| `lib/store.js` | 短信存储（JSON Lines）、去重查询、搜索、统计 |
| `lib/smtp.js` | 零依赖 SMTP 客户端、MIME 组装、邮件头编码 |
| `lib/format.js` | 验证码提取、时间格式化、邮件正文（纯文本 + HTML） |
| `public/` | 网页收件箱，原生 JS，无框架、无 CDN |

## 为什么零依赖

整个服务只用了 Node 内置模块（`http` / `net` / `tls` / `crypto` / `fs`）。
这意味着：

- 部署不需要 `npm install`，断网环境也能装
- 没有供应链风险，不会因为某个依赖被投毒而泄露邮箱授权码
- 镜像体积小、启动快（Docker 镜像只有几十 MB）

代价是 SMTP 协议要自己实现——但收信发信只需要 `EHLO / AUTH / MAIL / RCPT / DATA` 五条命令，
`lib/smtp.js` 一共 300 多行，覆盖了 465 隐式 TLS、587 STARTTLS，以及 QQ / 163 / Gmail / 企业邮的常见行为。

## 数据模型

一条短信在 `data/messages.json` 里占一行：

```json
{
  "id": "mvfd9rwx-169e1749",
  "from": "10690001",
  "content": "【某银行】您的验证码是 483920，5分钟内有效。",
  "code": "483920",
  "receivedAt": 1792591123635,
  "device": "备用机",
  "slot": "卡1",
  "source": "hook",
  "ip": "1.2.3.4",
  "mail": {
    "status": "sent",
    "attempts": 1,
    "at": 1792591124000,
    "error": null
  }
}
```

| 字段 | 说明 |
| --- | --- |
| `id` | 时间戳 36 进制 + 4 字节随机，天然按时间有序 |
| `code` | 自动提取的验证码，没识别到为 `null` |
| `slot` / `device` | 来自手机端的卡槽和设备备注，可选 |
| `mail.status` | `pending` / `retry` / `sent` / `failed` |
| `mail.error` | 最近一次失败原因，直接展示在网页上 |

文件采用「追加写 + 防抖整体重写」：新短信直接 append 一行（不会因为进程崩溃丢数据），
修改状态时重写整个文件（默认上限 5000 条，几十 KB 到几 MB，可忽略）。

## 重试策略

邮件投递失败后按固定退避重试，默认最多 6 次：

| 第几次失败 | 下次重试间隔 |
| --- | --- |
| 1 | 30 秒 |
| 2 | 2 分钟 |
| 3 | 10 分钟 |
| 4 | 30 分钟 |
| 5 | 2 小时 |
| 6 | 6 小时 / 之后标记为 failed |

进程重启后，所有 `pending` / `retry` 状态的短信会在启动 1.5 秒后重新排队，
所以「SMTP 宕机一小时」不会导致短信丢失——恢复后自动补发。

## 并发与顺序

- 入库路径是同步的（写文件 + 内存操作），不存在竞态
- 同一 `id` 的邮件投递有 `inflight` 集合去重，SSE 重连也不会重复发信
- SSE 只做通知，不承担数据一致性：前端收到事件后直接使用事件里的完整消息对象

## 安全模型

| 项 | 做法 |
| --- | --- |
| 手机端鉴权 | URL 路径里的 `hookToken`（128 位随机），可选 HMAC-SHA256 签名防重放 |
| 网页鉴权 | `adminToken`，请求头 `X-Auth-Token` 或 `?token=`；常量时间比较 |
| 令牌存储 | `config.json` 权限 600，只对服务用户可读 |
| 限流 | 同一 IP 每分钟 180 次，防止被当作开放中继刷爆 |
| 传输 | 建议全站 HTTPS；明文部署时令牌可被同网段嗅探 |
| 泄露面 | 网页接口不会返回邮箱授权码，只返回 `passSet: true/false` |

没有实现用户体系——这是单人自用的服务，多用户会增加复杂度和攻击面。
